## 3. Root causes found for the two known gaps

### `<<` / `&` on a symbol -- ONE bare `eval`, not a namespace table

Not a missing parser entry. `bitwise_and` AND `left_shift` are BOTH already present in every
re-parse table (`symbolic.py:2986-3072` `_PYSTR2SYM_locals`; `symbolic.py:2606-2655`
`_SerializedSymbolicParser._functions`), and `pystr_to_symbolic` round-trips both.

The NameError comes from **`dace/frontend/python/replacements/utils.py:236`**:

```python
pyval = eval(astutils.unparse(representative_value))    # no globals dict
```

A bare `eval` with no globals silently borrows `utils.py`'s module globals, which contain no
symbolic head name at all (measured: `bitwise_and`, `left_shift`, `int_floor`, and the `__`
variants are all absent). Reached whenever a symbolic operand meets an array/scalar --
`_array_sym_binop` / `_scalar_sym_binop`, `operators.py:657-706`.

⭐ **Why shifts survive the identical path and bitwise does not.** `sym_type` first substitutes a
representative value (`utils.py:216,235`). `left_shift.eval` / `right_shift.eval`
(`symbolic.py:1830-1843,1847-1860`) FOLD when both args are Numbers, so the expression collapses to
the literal `2` and `eval('2')` succeeds. `bitwise_and|or|xor|invert` are BODYLESS
(`symbolic.py:1812-1825`, `class bitwise_and(DaceFunction): pass`) -- no `eval`, no fold -- so the
string stays `bitwise_and(1, 3)` and the bare `eval` raises. Measured:

```
sym_type(left_shift(N,1))    -> OK int64_t
sym_type(int_floor(N,3))     -> OK int64_t      # folds too (symbolic.py:1481)
sym_type(bitwise_and(N,3))   -> NameError: name 'bitwise_and' is not defined
```

Frontend-side, `_pyop2symtype` (`replacements/operators.py:713-727`) has exactly ONE binary entry,
`"//" -> int_floor`. Patched to the BARE classes, shifts then work end to end INCLUDING inside a
map range (`for i in dace.map[0:(N >> 1)]`) -- measured, executed, correct. Patched to the
`__`-prefixed variants instead, codegen emits `__left_shift(N, 1)` into C++ and the build fails
(`'__left_shift' was not declared in this scope; did you mean 'left_shift'?`): those variants are
in NONE of `symbolic.py:3299`'s binop map, `2634-2643`, or `3009-3023`. They are half-wired --
produced by the parser, unknown to codegen.

⛔ `nqueens` shows the operand order matters too: `'int' and 'symbol'`, i.e. `1 << N`, the REVERSED
form. Any fix must cover both directions.

⛔ Correctness trap to avoid: `logical_left_shift` / `logical_right_shift` (`symbolic.py:1862-1895`)
are the Fortran ISHFT zero-fill lowering. Python's `>>` on a negative int is ARITHMETIC. Selecting
the logical variant from the python frontend would be a silent miscompile for negative operands,
not a missing feature.

### ListComp -- there is NO desugarer, at all

`grep -rn "ListComp|GeneratorExp|SetComp|DictComp|ast.comprehension"` over the whole dace tree
returns four sites, none of which rewrites anything:

- `newast.py:306-307` -- the `_DISALLOWED_STMTS` backstop;
- `preprocessing.py:1174-1176` -- a **commented-out** `elif` in `LoopUnroller.visit_For`;
- `codegen/cppunparse.py:893-925` -- four `raise NotImplementedError('Invalid C++')`;
- `sdfg/type_inference.py:727-745` -- four `pass` bodies.

No `visit_ListComp` / `visit_GeneratorExp` / `visit_SetComp` / `visit_DictComp` exists anywhere.
Comprehensions vanish today only as a SIDE EFFECT of whole-subtree constant folding through
`astutils.evalnode` (`astutils.py:77-106`), from three places: `LoopUnroller.visit_For`
(`preprocessing.py:1177-1186`), `GlobalResolver.visit_Subscript` (`preprocessing.py:716-751`), and
`GlobalResolver.visit_Call` (`preprocessing.py:775`, guarded by `resolve_functions`). So a
comprehension survives only when it is compile-time evaluable.

The `_DISALLOWED_STMTS` entry STAYS: it is the assertion that preprocessing already handled the
node, and deleting it would let an unhandled node reach code that assumes it cannot appear.
The fix is a desugarer.

## 4. The null-workspace protocol is still unexercised

What the pages claim is pinned; what they DESCRIBE has never run.
`skills/lang-cuda/SKILL.md:166-182` and `skills/lang-hip/SKILL.md:157-164` warn that a null
workspace makes the second CUB/rocPRIM call re-query the size and perform NO reduction, leaving the
output as found -- which on fresh device memory reads as a clean all-zero array with `cudaSuccess`.

The gate that would catch it is the ORACLE leg of scoring, not the determinism leg: an all-zero
result reproduces perfectly, so `_determinism_check` passes it. Whether any corpus kernel's correct
answer is all-zeros (or close enough at the grading tolerance) is the open question, and it is the
one that decides whether this is a coverage gap or a real hole.

## 5. Two other issues, root-caused

**cegterg skips 17 of 42 -- cause is one missing apt package.** `toolchain_available()`
(`tests/ports/cegterg/cegterg_reference_ctypes.py:47-56`) compiles a probe with
`-lfftw3 -llapack -lblas`; on this box it fails with `fatal error: fftw3.h: No such file or
directory`. `libfftw3-double3` (runtime) is installed, `libfftw3-dev` is NOT. blas/lapack are fine.
Confirmed by running: `25 passed, 17 skipped in 83.03s` -- 8 + 8 + 1 at
`test_cegterg_reference.py:207,221,236`. A legitimate optional-dependency skip, but a silent one.

**The numerical oracle bypasses the pet shim, and the Pluto merge did NOT fix it.**
`pluto_transform.py:75-97` `pet_parse_env()` shadows glibc's `<bits/math-vector.h>` for the polycc
subprocess, because pet extracts the scop with a flag-less libclang whose default aarch64 target
has no `neon` feature, so the `__neon_vector_type__` typedefs reject the whole TU before any scop is
seen. Its ONLY call site is `pluto_transform.py:143` inside `run_polycc`. The oracle at
`tests/numerical_oracle.py:1109` calls `["polycc", "--pet", ...]` through `_run_bounded` directly,
inheriting the ambient environment. x86_64 CI structurally cannot show this.
